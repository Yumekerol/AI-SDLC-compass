==============================================================================
DICIONÁRIO DE MÉTRICAS v2 - AI-SDLC Compass (scanner de repositório)
==============================================================================

OBJETIVO
  Definir as métricas que o scanner extrai de um repositório git para
  alimentar a LLM que escreve o relatório. Cada métrica foi escolhida por
  três critérios:

    1. Extraível só com git e análise estática (nada é executado, sem rede).
    2. Fiável o suficiente num repositório pequeno (até ~50 ficheiros).
    3. Sustenta uma decisão concreta sobre ONDE a IA pode ajudar no SDLC.
       Exemplo: nenhum teste encontrado -> geração de testes com IA.

  O scanner só emite factos. A ligação "métrica -> oportunidade de IA" está
  documentada aqui (campo "Porquê") e no Apêndice A, e é usada no prompt da
  LLM. Não faz parte do scanner, que continua determinístico.

  Este ficheiro serve também de glossário para a LLM: o "método" de cada
  métrica é estático e vive aqui, por isso não precisa de ser repetido no
  JSON de valores.

COMO LER CADA ENTRADA
  chave.no.json
    O que é   : definição da métrica
    Extração  : como se obtém (comando ou ferramenta)
    Porquê    : decisão de IA que a métrica sustenta
    Fase/Método/Prio : fase SDLC / exact ou heuristic / P1, P2 ou P3

  Fases SDLC (as do relatório): requirements, design, development, testing,
  deployment, monitoring.

  Método
    exact     : contagem ou existência de ficheiro; reproduzível.
    heuristic : depende de convenções, keywords ou aproximações. A LLM deve
                usar linguagem de indício ("sugere"), nunca de certeza.

  Prioridade
    P1 : essencial para o PoC
    P2 : recomendada
    P3 : opcional / se houver tempo

==============================================================================
REGRAS GERAIS
==============================================================================

  1. Só factos, nunca conclusões nem recomendações.
  2. Ausência não é inexistência. Cada bloco regista o que foi procurado
     (checked) e não encontrado (not_found). A LLM deve escrever "não
     encontrado no repositório", nunca "não existe". Testes, CI ou docs
     podem viver noutro repositório.
  3. Método é estático (definido aqui). Confiança é dinâmica: as métricas
     baseadas em histórico herdam data_quality.history_confidence.
  4. Determinismo: versões das ferramentas fixas e registadas no meta;
     listas ordenadas de forma estável; resultado ligado ao SHA do HEAD;
     sem rede; nenhum código do repo é executado.
  5. ref_date é um parâmetro opcional (ex.: data da entrevista). Por
     omissão é a data do último commit. Nunca se usa a data do sistema.
  6. evidence = paths, SHAs, nomes de funções. Nunca código-fonte nem
     valores de segredos.
  7. Só agregados de equipa. Nunca métricas por pessoa.
  8. Sem scores compostos ("AI readiness 73/100"). Usam-se factos e níveis
     ordinais com a regra declarada (ver derived.guardrails).
  9. Se um módulo falhar, o resto continua e collector_status regista-o.

==============================================================================
LIMIARES POR OMISSÃO (configuráveis em thresholds.yaml e declarados no meta)
==============================================================================

  complexidade ciclomática alta ........ CCN >= 10
  função longa ......................... > 50 linhas (NLOC)
  muitos parâmetros .................... > 5
  ficheiro grande ...................... > 500 e > 1000 linhas
  commit grande ........................ > 500 linhas alteradas
  mensagem genérica .................... < 10 caracteres ou na lista
                                         (wip, fix, update, misc, test, .)
  hotspot .............................. churn e complexidade no percentil
                                         >= p75 (adequado a ~50 ficheiros)
  janela de churn ...................... últimos 12 meses
  ficheiro reincidente em correções .... >= 3 commits de correção
  dono único (ficheiro) ................ >= 80% das linhas
  dono único (hotspot) ................. >= 85% das linhas
  ficheiro parado ...................... > 365 dias sem alteração
  autor ativo .......................... commit nos últimos 90 dias
  change coupling ...................... >= 5 co-alterações e >= 60% das
                                         alterações do ficheiro menos mexido;
                                         ignora commits com > 20 ficheiros
  history_confidence ................... low: < 30 commits OU < 4 semanas OU
                                         shallow. high: >= 100 commits E
                                         >= 12 semanas. medium: restantes.
  typing_level (Python) ................ low < 20%, partial 20-80%, high > 80%

==============================================================================
FERRAMENTAS NECESSÁRIAS
==============================================================================

  Obrigatórias : git, scc (ou tokei), lizard, PyYAML, pathspec, módulo ast
                 do Python (docstrings e tipagem em Python)
  Recomendada  : tree-sitter (docstrings, tipagem e tratamento de erros em
                 JavaScript e Java)
  Opcionais    : jscpd (duplicação), gitleaks (segredos; fallback: conjunto
                 de regex offline)

==============================================================================
DICIONÁRIO
==============================================================================

------------------------------------------------------------------------------
A. META
------------------------------------------------------------------------------

meta
  O que é   : identificação do scan: schema_version, repo_head (SHA),
              ref_date, tool_versions e thresholds_hash.
  Extração  : git rev-parse HEAD; git log -1 --format=%aI; versões das
              ferramentas; hash do thresholds.yaml.
  Porquê    : garante reprodutibilidade (mesmo repo + mesma config = mesmo
              output) e permite citar a versão exata que foi analisada.
  Fase/Método/Prio : todas / exact / P1

------------------------------------------------------------------------------
B. DATA_QUALITY (quanto se pode confiar nos dados)
------------------------------------------------------------------------------

data_quality.commits_total
  O que é   : número de commits no histórico analisado (bruto, inclui bots).
  Extração  : git rev-list --count HEAD
  Porquê    : base de confiança de todas as métricas de histórico.
  Fase/Método/Prio : todas / exact / P1

data_quality.span_weeks
  O que é   : semanas entre o primeiro e o último commit.
  Extração  : git log --format=%aI (primeiro e último).
  Porquê    : histórico curto torna médias e tendências pouco fiáveis.
  Fase/Método/Prio : todas / exact / P1

data_quality.days_since_last_commit
  O que é   : dias entre o último commit e a ref_date fornecida.
  Extração  : só calculado se ref_date for passada por parâmetro; caso
              contrário é null.
  Porquê    : repo parado pode não ser o repositório ativo da equipa.
              Alimenta a observação dormant_repo.
  Fase/Método/Prio : todas / exact / P2

data_quality.is_shallow
  O que é   : se o clone tem histórico truncado.
  Extração  : git rev-parse --is-shallow-repository
  Porquê    : um shallow clone invalida quase todas as métricas de histórico.
  Fase/Método/Prio : todas / exact / P1

data_quality.squash_suspected
  O que é   : suspeita de merges feitos por squash.
  Extração  : >= 50% dos assuntos de commit terminam em "(#N)" e merge
              commits < 2% do total.
  Porquê    : squash destrói granularidade; tamanho dos commits, bus factor
              e commits diretos na main ficam distorcidos.
  Fase/Método/Prio : todas / heuristic / P2

data_quality.bot_commit_share
  O que é   : % de commits feitos por bots (dependabot, renovate,
              github-actions, [bot]).
  Extração  : nome e email do autor (após .mailmap).
  Porquê    : bots não são equipa; os agregados humanos excluem-nos.
  Fase/Método/Prio : todas / heuristic / P2

data_quality.history_confidence
  O que é   : nível derivado (low / medium / high) de confiança no histórico.
  Extração  : regra dos limiares (commits, semanas, shallow).
  Porquê    : com low, a LLM não pode afirmar tendências nem métricas de
              histórico sem confirmação da equipa.
  Fase/Método/Prio : todas / exact / P1

data_quality.file_inventory
  O que é   : ficheiros analisados e ignorados por categoria (vendor,
              node_modules, gerados, minificados, lockfiles, binários,
              > 1 MB).
  Extração  : git ls-files + pathspec + .gitattributes (linguist-generated,
              linguist-vendored) + heurística de minificados.
  Porquê    : evita que lixo distorça LOC, linguagens e complexidade.
  Fase/Método/Prio : todas / exact / P1

data_quality.collector_status
  O que é   : estado (ok / partial / failed / unavailable) de cada módulo
              do scanner, com razão curta.
  Extração  : registado pelo próprio scanner.
  Porquê    : a LLM não pode concluir "não há testes" se o módulo de testes
              falhou.
  Fase/Método/Prio : todas / exact / P1

------------------------------------------------------------------------------
C. PROJECT_PROFILE (o que o repositório é de facto)
------------------------------------------------------------------------------

project_profile.lang_share
  O que é   : % de linhas de código (sem comentários nem linhas em branco)
              por linguagem, sem vendor, gerados, minificados e lockfiles.
  Extração  : scc --by-file --format json (ou tokei), sobre os ficheiros de
              file_inventory.
  Porquê    : define em que linguagens a IA tem de trabalhar e apanha
              divergências entre o declarado e o real (ex.: a equipa diz
              JavaScript e o código é Python).
  Fase/Método/Prio : development / exact / P1

project_profile.lang_share_by_folder
  O que é   : a mesma distribuição por pasta de topo.
  Extração  : agregação do output do scc por diretório.
  Porquê    : revela repos mistos (frontend/ + backend/) e onde vive cada
              linguagem.
  Fase/Método/Prio : design / exact / P2

project_profile.language_role
  O que é   : papel de cada linguagem: aplicação ou apenas tooling de
              build/scripts (ex.: build_tooling_only).
  Extração  : JS só em devDependencies/scripts de build, pastas
              scripts/tools/build e poucos LOC.
  Porquê    : explica a divergência de stack sem a interpretar.
  Fase/Método/Prio : development / heuristic / P2

project_profile.manifests_and_lockfiles
  O que é   : manifestos (package.json, requirements*.txt, pyproject.toml,
              Pipfile, pom.xml, build.gradle) e lockfiles presentes.
  Extração  : git ls-files.
  Porquê    : mostra o ecossistema real e a reprodutibilidade das builds.
  Fase/Método/Prio : development / exact / P2

project_profile.frameworks
  O que é   : frameworks, ORM e base de dados inferidos das dependências
              declaradas (django, flask, fastapi, express, react,
              spring-boot, sqlalchemy, mongoose, postgres...).
  Extração  : parse dos manifestos + catálogo fixo de nomes normalizados.
  Porquê    : determina o que a IA deve gerar: testes de endpoints numa API,
              validação de dados num pipeline, componentes num frontend.
  Fase/Método/Prio : development / exact / P1

project_profile.project_type
  O que é   : api_backend | frontend | data_ml | library | cli | infra | mixed
  Extração  : regras sobre frameworks, pastas e ficheiros (rotas, notebooks,
              entry points, ficheiros só YAML/HCL).
  Porquê    : a mesma oportunidade de IA muda de forma conforme o tipo.
  Fase/Método/Prio : design / heuristic / P2

project_profile.runtimes
  O que é   : versão de runtime e se está fora de suporte (eol).
  Extração  : .python-version, .nvmrc, engines do package.json, FROM do
              Dockerfile, setup-python/setup-node nos workflows, java.version
              no pom; comparação com tabela EOL offline, relativa à ref_date.
  Porquê    : runtime fora de suporte -> upgrades e migrações assistidos.
  Fase/Método/Prio : deployment / exact / P3

project_profile.repo_size
  O que é   : nº de ficheiros, LOC e tokens aproximados (bytes / 4).
  Extração  : scc + tamanho em bytes dos ficheiros analisados.
  Porquê    : define se uma ferramenta de IA vê o repo inteiro ou só por
              módulos (alimenta guardrails.repo_fits_in_context).
  Fase/Método/Prio : development / exact / P2

------------------------------------------------------------------------------
D. TESTING (sem executar nada)
------------------------------------------------------------------------------

testing.test_inventory
  O que é   : {files, functions} = nº de ficheiros e de funções de teste.
  Extração  : ficheiros por convenção (test_*.py, *_test.py, *.test.js,
              *.spec.js, *Test.java, pastas tests/, test/, __tests__/,
              src/test/); funções por padrão (def test_, @Test, it(, test( ).
  Porquê    : sinal base. Zero testes encontrados -> hipótese "geração de
              testes com IA" (Apêndice A, A1). Atenção: "não encontrados"
              pode significar testes noutro repositório.
  Fase/Método/Prio : testing / heuristic / P1

testing.test_frameworks
  O que é   : frameworks de teste detetados (pytest, unittest, jest, mocha,
              vitest, junit, testng).
  Extração  : dependências nos manifestos + imports nos ficheiros de teste.
  Porquê    : a IA deve gerar testes no framework que a equipa já usa.
  Fase/Método/Prio : testing / exact / P1

testing.test_code_ratio
  O que é   : LOC de testes a dividir por LOC de código, global e por pasta
              de topo.
  Extração  : scc sobre ficheiros classificados como teste vs. código.
  Porquê    : separa "sem testes" de "poucos testes".
  Fase/Método/Prio : testing / exact / P1

testing.test_types
  O que é   : tipos de teste presentes (unit, integration, e2e).
  Extração  : pastas (unit/, integration/, e2e/) e frameworks (cypress,
              playwright, selenium, supertest, testcontainers).
  Porquê    : lacunas de integração e e2e são candidatas a geração de
              cenários de teste com IA.
  Fase/Método/Prio : testing / heuristic / P2

testing.untested_modules
  O que é   : módulos de código sem teste associado, ordenados por
              complexidade.
  Extração  : convenção de nomes (foo.py <-> test_foo.py; foo.js <->
              foo.test.js; Foo.java <-> FooTest.java; espelho de pastas).
  Porquê    : mostra onde falta rede de segurança; alimenta complex_untested
              e bug_magnets. O relatório deve assumir que o mapeamento é
              heurístico.
  Fase/Método/Prio : testing / heuristic / P1

testing.coverage_config
  O que é   : se existe configuração de cobertura ou relatórios commitados.
  Extração  : .coveragerc, [tool.coverage] no pyproject, coverageThreshold
              no jest, jacoco no pom/gradle, coverage.xml, lcov.info.
  Porquê    : sem medição de cobertura, não há como avaliar o ganho de testes
              gerados por IA.
  Fase/Método/Prio : testing / exact / P2

testing.test_commit_share
  O que é   : % de commits que alteram código-fonte e também ficheiros de
              teste.
  Extração  : git log --name-only + classificação de paths.
  Porquê    : distingue "existem testes" de "testar é hábito". Valor baixo
              -> IA para gerar testes junto de cada alteração.
  Fase/Método/Prio : testing / heuristic / P2

------------------------------------------------------------------------------
E. CODE_HEALTH (qualidade do código atual)
------------------------------------------------------------------------------

code_health.cyclomatic_complexity
  O que é   : complexidade ciclomática por função: p50, p90, máximo e top-10
              (ficheiro:função:CCN).
  Extração  : lizard --csv -l python -l javascript -l java
  Porquê    : mostra onde o código é difícil de manter e testar; candidatos
              a refactoring e testes assistidos.
  Fase/Método/Prio : development / exact / P1

code_health.function_smells
  O que é   : funções longas (> 50 NLOC) e com muitos parâmetros (> 5):
              contagens e top-5.
  Extração  : campos length e PARAM do output do lizard.
  Porquê    : candidatos a extração de funções e refactoring assistido.
  Fase/Método/Prio : development / exact / P2

code_health.large_files
  O que é   : nº de ficheiros com mais de 500 e de 1000 linhas.
  Extração  : scc --by-file.
  Porquê    : alvos de modularização e limite prático para ferramentas de
              IA com contexto finito.
  Fase/Método/Prio : development / exact / P2

code_health.duplication_and_boilerplate
  O que é   : duplication_pct (% de código duplicado) e similar_file_groups
              (grupos de ficheiros com o mesmo padrão de nome e estrutura
              parecida: controllers, DTOs, rotas CRUD).
  Extração  : jscpd --reporters json; grupos por padrão de nome + tamanho e
              hash estrutural (aproximado).
  Porquê    : trabalho repetitivo é o caso mais direto de IA (geração de
              boilerplate, consolidação de duplicados).
  Fase/Método/Prio : development / exact (%) e heuristic (grupos) / P2

code_health.docstring_coverage
  O que é   : % de funções e classes públicas com docstring, JSDoc ou
              Javadoc.
  Extração  : Python: módulo ast; JavaScript e Java: tree-sitter.
  Porquê    : valor baixo -> geração e manutenção de documentação com IA, uma
              das aplicações mais maduras.
  Fase/Método/Prio : development / heuristic / P1

code_health.typing_level
  O que é   : Python: % de funções com anotações de tipo; JavaScript: peso de
              .ts/.tsx e tsconfig strict; Java: n/a (tipagem estática).
              Inclui level derivado (low / partial / high).
  Extração  : ast (Python); extensões e tsconfig.json (JS).
  Porquê    : a tipagem é rede de segurança para código gerado por IA.
              Nível baixo -> introduzir tipos antes de refactoring grande.
  Fase/Método/Prio : development / heuristic / P2

code_health.tech_debt_markers
  O que é   : contagem de TODO/FIXME/HACK/XXX e ficheiros com mais marcadores.
  Extração  : grep nos ficheiros analisados.
  Porquê    : dívida declarada pela própria equipa -> backlog natural para
              triagem e resolução assistidas.
  Fase/Método/Prio : development / exact / P2

code_health.weak_error_handling
  O que é   : except: nu ou except Exception: pass (Python); catch vazio
              (JavaScript e Java).
  Extração  : tree-sitter ou regex sobre os padrões.
  Porquê    : falhas silenciosas dificultam debugging; revisão assistida do
              tratamento de erros e instrumentação.
  Fase/Método/Prio : development / exact (padrões) / P2

------------------------------------------------------------------------------
F. DEVELOPMENT_PROCESS (hábitos de trabalho, vistos pelo histórico git)
------------------------------------------------------------------------------

development_process.churn_by_file
  O que é   : por ficheiro, nº de commits e linhas adicionadas/apagadas na
              janela de churn; top-10.
  Extração  : git log --no-merges --numstat --format='@@%H|%aI|%aN|%s'
              (uma só passagem, parse em Python).
  Porquê    : base dos hotspots. Churn alto sozinho não é mau (ficheiros de
              configuração e rotas mudam muito); cruza-se sempre com
              complexidade.
  Fase/Método/Prio : development / exact / P1

development_process.commit_size
  O que é   : p50 e p90 de linhas e de ficheiros por commit; % de commits
              com mais de 500 linhas.
  Extração  : numstat da mesma passagem.
  Porquê    : commits grandes são difíceis de rever -> pré-revisão e
              sumarização de alterações com IA.
  Fase/Método/Prio : development / exact / P1

development_process.commit_message_quality
  O que é   : comprimento mediano, % de mensagens genéricas, % que segue
              Conventional Commits.
  Extração  : regex sobre os assuntos dos commits.
  Porquê    : mensagens fracas -> geração de mensagens de commit e changelogs
              com IA.
  Fase/Método/Prio : development / heuristic / P2

development_process.traceability
  O que é   : % de commits com referência a issue (#123 ou PROJ-123) e
              prefixo dominante.
  Extração  : regex #\d+ e [A-Z][A-Z0-9]+-\d+ nos assuntos.
  Porquê    : pouca rastreabilidade requisitos <-> código -> IA para ligar
              commits e PRs a requisitos. O prefixo (PROJ- sugere Jira, #
              sugere GitHub) cruza com a ferramenta que a equipa declarar.
  Fase/Método/Prio : requirements / heuristic / P1

development_process.merge_and_branching
  O que é   : rácio merges/commits; prefixos de branch (feature/, hotfix/,
              release/); % de commits diretos na branch principal.
  Extração  : git log --merges; prefixos lidos dos assuntos de merge e de
              git branch -r; git log --first-parent --no-merges para os
              commits diretos.
  Porquê    : contrasta a metodologia declarada (Scrum, Kanban, Waterfall)
              com o observado. Sem merges nem PRs -> hipótese de revisão
              de código com IA. Cuidado com squash (ver squash_suspected).
  Fase/Método/Prio : development / heuristic / P1

development_process.change_coupling
  O que é   : pares de ficheiros que mudam juntos com frequência.
  Extração  : co-ocorrência no git log --name-only (limiares acima).
  Porquê    : dependências escondidas -> análise de impacto e documentação
              de arquitetura assistidas.
  Fase/Método/Prio : design / heuristic / P3

------------------------------------------------------------------------------
G. STABILITY (indícios de instabilidade; nunca "taxa de defeitos")
------------------------------------------------------------------------------

stability.fix_commit_ratio
  O que é   : % de commits cujo assunto contém fix, bug, hotfix, patch ou
              regress.
  Extração  : regex case-insensitive sobre os assuntos.
  Porquê    : indicador fraco, mas útil. Valor alto -> revisão estática
              assistida e testes dirigidos.
  Fase/Método/Prio : testing / heuristic / P1

stability.repeat_fix_files
  O que é   : ficheiros tocados por 3 ou mais commits de correção (top).
  Extração  : cruzamento fix commits x numstat por ficheiro.
  Porquê    : módulos reincidentes mostram onde investir primeiro em testes
              e revisão com IA.
  Fase/Método/Prio : testing / heuristic / P1

stability.reverts
  O que é   : nº de commits de revert.
  Extração  : git log --grep='^Revert "' (e "This reverts commit").
  Porquê    : alterações arriscadas sem rede de segurança.
  Fase/Método/Prio : testing / exact / P2

------------------------------------------------------------------------------
H. KNOWLEDGE (concentração de conhecimento, em agregado)
------------------------------------------------------------------------------

knowledge.bus_factor
  O que é   : nº mínimo de autores que cobrem 50% das linhas atuais, mais
              single_owner_file_share (% de ficheiros com um autor >= 80%
              das linhas).
  Extração  : git blame --line-porcelain -w -M por ficheiro, com .mailmap e
              sem bots. Barato em repos de até ~50 ficheiros; em maiores,
              limitar aos top-N por complexidade ou churn.
  Porquê    : conhecimento concentrado -> IA para explicar código,
              documentar e acelerar onboarding. Autores com vários emails
              distorcem o valor; sinalizar quando não há .mailmap.
  Fase/Método/Prio : development / exact / P1

knowledge.stale_files
  O que é   : % de ficheiros sem alteração há mais de 365 dias e % de linhas
              com mais de 1 ano.
  Extração  : git log -1 --format=%aI -- <ficheiro>; datas do blame.
  Porquê    : legado parado, normalmente sem docs nem testes -> IA para
              compreensão e modernização cautelosa.
  Fase/Método/Prio : development / exact / P2

knowledge.active_authors
  O que é   : autores humanos ativos nos últimos 90 dias vs. total
              histórico (agregado).
  Extração  : git log com .mailmap, sem bots.
  Porquê    : tamanho real da equipa e saída de pessoas; cruza com o tamanho
              de equipa declarado.
  Fase/Método/Prio : development / exact / P2

------------------------------------------------------------------------------
I. DOCS_REQUIREMENTS (o pouco que o repo mostra de requisitos e design)
------------------------------------------------------------------------------

docs_requirements.docs_inventory
  O que é   : presença e path de README (com secções detetadas: instalação,
              uso, arquitetura), CHANGELOG, ADRs, OpenAPI/Swagger, diagramas
              (.puml, .mmd, .drawio), specs Gherkin (.feature) e docs/.
  Extração  : git ls-files + cabeçalhos do README.
  Porquê    : ausência -> IA para refinar user stories, documentar
              arquitetura e gerar OpenAPI a partir do código. Reportar como
              "não visível no repositório".
  Fase/Método/Prio : requirements, design / exact / P1

docs_requirements.doc_drift_days
  O que é   : dias entre a última alteração de README/docs e o último commit
              de código.
  Extração  : git log -1 --format=%aI -- <paths de docs> vs. de código.
  Porquê    : documentação desatualizada -> manutenção de docs com IA.
  Fase/Método/Prio : design / exact / P2

docs_requirements.process_artifacts
  O que é   : templates de PR e de issue, CONTRIBUTING, CODEOWNERS,
              SECURITY.md.
  Extração  : git ls-files (.github/, raiz).
  Porquê    : processo formalizado ou não. CODEOWNERS indica aprovações
              obrigatórias (contexto para queixas de permissões, não prova).
  Fase/Método/Prio : requirements / exact / P2

------------------------------------------------------------------------------
J. TOOLING (inventário normalizado)
------------------------------------------------------------------------------

tooling.detected / tooling.not_found / tooling.mentioned
  O que é   : três listas.
              detected  : ferramenta, categoria e evidência.
              not_found : o que foi procurado sem resultado.
              mentioned : ferramentas sem rasto técnico possível (Jira,
              Confluence, Slack, Notion, Trello) vistas em README, docs ou
              commits.
  Extração  : tools_catalog.yaml com nomes normalizados (jenkins,
              github_actions, gitlab_ci, eslint, ruff, flake8, black,
              prettier, mypy, pytest, jest, docker, terraform, sonar,
              postman, pre_commit, dependabot, renovate...), por ficheiros
              de configuração, dependências e secções de pyproject.
  Porquê    : cruza com o que a equipa disser ("usamos Jenkins"). Mostra
              que linter, formatador e CI existem e que lacunas a IA pode
              preencher.
  Fase/Método/Prio : todas / exact (detected, not_found) e heuristic
                     (mentioned) / P1

------------------------------------------------------------------------------
K. DELIVERY (CI/CD e deploy, só o que o repo mostra)
------------------------------------------------------------------------------

delivery.ci_pipelines
  O que é   : sistemas de CI encontrados, com jobs/stages classificados em
              lint, test, build, security e deploy, e triggers (push, PR,
              tag, manual).
  Extração  : parse de .github/workflows/*.yml, .gitlab-ci.yml,
              azure-pipelines.yml; regex stage() no Jenkinsfile;
              classificação por comando (pytest, npm test, mvn test, eslint,
              ruff, trivy, bandit, docker build, kubectl, terraform apply).
  Porquê    : pipeline sem lint, teste ou segurança -> configuração
              assistida de pipeline. Sem pipeline -> começar por criá-lo.
  Fase/Método/Prio : deployment / exact (ficheiros) e heuristic
                     (classificação) / P1

delivery.deploy_automation
  O que é   : se o pipeline tem passo de deploy, alvo identificável
              (registry, k8s, cloud, ssh, pages) e indícios de deploy
              manual (deploy.sh, alvo deploy no Makefile, runbooks).
  Extração  : comandos e actions nos pipelines; ficheiros de script.
  Porquê    : deploy manual -> IA para gerar pipelines e IaC. Não mostra a
              frequência real de deploys nem tempos de espera.
  Fase/Método/Prio : deployment / heuristic / P1

delivery.environments
  O que é   : ambientes referenciados (dev, staging, production) e se há
              required reviewers de ambiente nos workflows.
  Extração  : chaves environment nos workflows e ficheiros de config.
  Porquê    : contexto para queixas sobre aprovações. A branch protection
              real não é visível sem API.
  Fase/Método/Prio : deployment / exact / P2

delivery.iac_and_containers
  O que é   : Dockerfile (imagem base, multi-stage), docker-compose,
              manifests k8s, Helm, Terraform, Ansible, Makefile.
  Extração  : git ls-files + conteúdo mínimo (FROM, kind:).
  Porquê    : grau de automação da infraestrutura; ausência -> geração
              assistida de Dockerfile e IaC.
  Fase/Método/Prio : deployment / exact / P2

delivery.dependency_automation
  O que é   : dependabot/renovate, pre-commit, lockfiles e nº de
              dependências diretas.
  Extração  : ficheiros de config e manifestos.
  Porquê    : sem bot nem lockfile -> IA para upgrades e migrações.
  Fase/Método/Prio : deployment / exact / P2

delivery.release_cadence
  O que é   : nº de tags, intervalo mediano entre tags (dias), % semver e
              presença de CHANGELOG.
  Extração  : git tag --sort=creatordate --format='%(refname:short)|%(creatordate:iso-strict)'
  Porquê    : proxy da frequência de entrega (não a real). Sem tags -> IA
              para release notes e changelogs.
  Fase/Método/Prio : deployment / exact / P2

------------------------------------------------------------------------------
L. OBSERVABILITY (monitorização: a fase com menos visibilidade no repo)
------------------------------------------------------------------------------

observability.logging_practice
  O que é   : bibliotecas de logging usadas (logging, structlog, loguru,
              winston, pino, slf4j, log4j), se o formato é estruturado e
              print_vs_logger_ratio = print / (print + logger).
  Extração  : imports e contagem de chamadas print( / console.log( vs.
              logger.
  Porquê    : logs pobres -> estruturação e instrumentação assistidas;
              melhor debugging.
  Fase/Método/Prio : monitoring / heuristic / P2

observability.monitoring_tooling
  O que é   : Sentry, prometheus_client, Micrometer, OpenTelemetry, SDKs de
              Datadog/New Relic; endpoints de health (/health, /healthz,
              /ready).
  Extração  : dependências, imports e padrões de rotas.
  Porquê    : sem métricas, tracing ou erros -> instrumentação assistida.
  Fase/Método/Prio : monitoring / exact / P2

------------------------------------------------------------------------------
M. SECURITY (sobretudo guardrails para o uso de IA)
------------------------------------------------------------------------------

security.secrets_exposed
  O que é   : nº, path:linha e tipo de segredos no working tree e no
              histórico. Nunca o valor.
  Extração  : gitleaks detect --redact (ou conjunto de regex offline).
  Porquê    : não é oportunidade de IA, é guardrail: segredos têm de ser
              removidos e rodados antes de qualquer ferramenta de IA ver o
              código.
  Fase/Método/Prio : deployment / heuristic / P1

security.env_files_committed
  O que é   : ficheiros sensíveis versionados (.env, *.pem, id_rsa,
              credentials*), se o .gitignore os cobre e se há .env.example.
  Extração  : git ls-files + leitura do .gitignore.
  Porquê    : higiene básica e guardrail.
  Fase/Método/Prio : deployment / exact / P2

security.security_scanning
  O que é   : SAST ou scan de dependências configurados (bandit, semgrep,
              codeql, trivy, snyk, npm audit, OWASP dependency-check).
  Extração  : pipelines e ficheiros de configuração.
  Porquê    : ausência -> configuração assistida de scans e triagem de
              alertas.
  Fase/Método/Prio : deployment / exact / P2

security.sensitive_data_markers
  O que é   : nº de ficheiros e campos com identificadores de dados pessoais
              (email, nif, iban, password, ssn, birth, health) e menções a
              GDPR, PCI, HIPAA nos docs.
  Extração  : regex sobre identificadores em código e schemas; grep nos docs.
  Porquê    : guardrail de privacidade: com dados pessoais, usar IA só em
              código sem dados reais e com ferramentas aprovadas.
  Fase/Método/Prio : development / heuristic / P3

------------------------------------------------------------------------------
N. AI_USAGE (IA já existente, sempre em chaves separadas)
------------------------------------------------------------------------------

ai_usage.in_development
  O que é   : ficheiros de contexto de IA (AGENTS.md, CLAUDE.md,
              .cursorrules, .cursor/, .github/copilot-instructions.md,
              .aider*, .continue/) e trailers de commit (Co-authored-by com
              Copilot/Claude/Cursor, "Generated with").
  Extração  : git ls-files + grep nos trailers (git log --format=%B).
  Porquê    : mede a adoção real de IA no desenvolvimento e contrasta com a
              maturidade declarada pela equipa.
  Fase/Método/Prio : development / exact (ficheiros) e heuristic (trailers)
                     / P1

ai_usage.in_product
  O que é   : SDKs de IA nas dependências (openai, anthropic, langchain,
              transformers, llama-index...).
  Extração  : manifestos.
  Porquê    : IA NO PRODUTO. Reportada à parte: não é adoção de IA no
              desenvolvimento e não deve ser confundida com ela.
  Fase/Método/Prio : development / exact / P2

------------------------------------------------------------------------------
O. TRENDS (um número diz "como está", uma tendência diz "para onde vai")
------------------------------------------------------------------------------

trends.commits_per_month / active_authors_per_quarter /
trends.fix_share_per_quarter / test_commit_share_per_quarter
  O que é   : quatro séries temporais.
              commits_per_month             : atividade
              active_authors_per_quarter    : pessoas ativas
              fix_share_per_quarter         : % de commits de correção
              test_commit_share_per_quarter : % de commits que tocam testes
  Extração  : agrupamento por mês/trimestre dos dados da passagem única do
              git log (custo marginal quase nulo).
  Porquê    : permite dizer "atividade a cair", "testes abandonados",
              "bugs a aumentar", "conhecimento a concentrar-se".
              Só emitidas se history_confidence >= medium; caso contrário,
              status "insufficient_history".
  Fase/Método/Prio : development, testing / exact (commits, autores) e
                     heuristic (correções, testes) / P2

------------------------------------------------------------------------------
P. DERIVED (cruzamentos entre métricas, ainda determinísticos)
------------------------------------------------------------------------------

derived.hotspots
  O que é   : ficheiros com churn E complexidade no percentil >= p75.
              Campos: path, churn_commits, lines_changed, cc_max,
              top_author_share, has_mapped_test, fix_commits.
  Extração  : churn_by_file x cyclomatic_complexity (agregado por ficheiro)
              x untested_modules x repeat_fix_files x bus_factor.
  Porquê    : os candidatos mais fortes para IA em refactoring, revisão e
              testes de caracterização.
  Fase/Método/Prio : development, testing / heuristic / P1

derived.complex_untested
  O que é   : funções com CCN >= 10 cujo módulo não tem teste mapeado (top-10).
  Extração  : cyclomatic_complexity x untested_modules.
  Porquê    : prioridade de geração de testes com IA.
  Fase/Método/Prio : testing / heuristic / P1

derived.bug_magnets
  O que é   : ficheiros reincidentes em correções e sem teste mapeado.
  Extração  : repeat_fix_files x untested_modules.
  Porquê    : os pontos mais frágeis do código.
  Fase/Método/Prio : testing / heuristic / P2

derived.single_owner_hotspots
  O que é   : hotspots com um autor acima de 85% das linhas.
  Extração  : hotspots x bus_factor.
  Porquê    : risco de conhecimento no código crítico -> documentação e
              explicação de código assistidas.
  Fase/Método/Prio : development / exact / P2

derived.guardrails
  O que é   : factos que condicionam as recomendações (sem score composto):
              has_tests, ci_runs_tests, has_linter, has_formatter,
              typing_level, repo_fits_in_context, secrets_present,
              history_confidence.
  Extração  : derivados de test_inventory, ci_pipelines, tooling,
              typing_level, repo_size, secrets_exposed e data_quality.
  Porquê    : evita recomendar o impossível. Ex.: sem testes e sem CI, a
              recomendação passa a ser "primeiro rede de segurança, depois
              IA em refactoring" (Apêndice A, G1).
  Fase/Método/Prio : todas / exact / P1

derived.internal_observations
  O que é   : lista de flags factuais de incoerência no próprio repo, sem
              interpretação. Servem de pista para a LLM confirmar com a
              equipa.
              manifest_without_code   : package.json presente e < 5% de LOC
                                        JS/TS
              code_without_manifest   : > 500 LOC de uma linguagem sem
                                        manifesto de dependências
              ci_without_test_stage   : há CI mas sem passo de teste
              tests_not_in_ci         : há testes e nenhum pipeline os corre
              tool_configured_not_used: configuração de ferramenta sem
                                        ficheiros da linguagem (ex.:
                                        .eslintrc com 0 ficheiros JS)
              docs_stale              : docs sem alterações > 365 dias com
                                        código ativo nos últimos 90 dias
              single_author_hotspots  : ver derived.single_owner_hotspots
              dormant_repo            : > 90 dias entre o último commit e a
                                        ref_date (só se ref_date fornecida)
  Extração  : condições acima sobre as métricas base.
  Porquê    : são o tipo de achado que mais valor tem num relatório: o que o
              repo mostra e a equipa não disse, ou o contrário.
  Fase/Método/Prio : todas / exact / P1

------------------------------------------------------------------------------
Q. EXAMPLES E NOT_OBSERVABLE
------------------------------------------------------------------------------

examples
  O que é   : 3 a 5 casos concretos por tipo (untested_complex, repeat_fix,
              weak_commit_message, undocumented_public_api,
              single_owner_hotspot), com path, função, SHA e valores.
  Extração  : top-N determinístico (ordenado por valor e depois por path).
  Porquê    : com nomes concretos a LLM escreve "o orders.py tem
              complexidade 27 e nenhum teste" em vez de "há código
              complexo". Nunca inclui código, só referências.
  Fase/Método/Prio : todas / exact / P1

not_observable
  O que é   : lista fixa, sempre incluída, do que um repositório nunca
              mostra.
  Extração  : estática.
  Porquê    : impede a LLM de inventar. Estes temas só vêm da conversa com a
              equipa.
              permission_wait_times, lead_and_cycle_time,
              real_deploy_frequency, incidents_and_recovery,
              requirements_quality, pr_review_time, real_test_coverage,
              test_flakiness, team_skills, compliance_and_allowed_tools,
              manual_processes_outside_repo
  Fase/Método/Prio : todas / exact / P1

==============================================================================
APÊNDICE A - COMO A LLM USA AS MÉTRICAS (fora do scanner)
==============================================================================

Esta tabela é conhecimento para o prompt da LLM, não lógica do scanner. A LLM
deve apresentar cada ponto como hipótese com a evidência citada, e não como
conclusão.

OPORTUNIDADES (sinal -> hipótese de IA [fase])

  A1  test_inventory.files = 0 (nenhum teste encontrado)
        -> geração de testes unitários com IA, no framework dominante da
           stack [testing]
  A2  complex_untested ou untested_modules não vazios
        -> testes dirigidos às funções mais complexas sem teste [testing]
  A3  fix_commit_ratio alto + repeat_fix_files / bug_magnets
        -> testes de regressão e revisão estática assistida nesses
           ficheiros [testing]
  A4  hotspots (churn x complexidade)
        -> refactoring assistido, precedido de testes de caracterização
           [development]
  A5  commit_size.p90 alto + merge_ratio baixo ou direct_commits_main_share
      alto
        -> pré-revisão de código e sumarização de alterações [development]
  A6  docstring_coverage baixo ou doc_drift_days alto
        -> geração e atualização de documentação [development, design]
  A7  bus_factor <= 2 ou single_owner_hotspots
        -> explicação de código, documentação e onboarding assistidos
           [development]
  A8  commit_message_quality fraca ou traceability baixa
        -> mensagens de commit, changelogs e ligação commits <-> requisitos
           [requirements, development]
  A9  docs_inventory sem specs, ADRs nem OpenAPI
        -> refinamento de user stories, documentação de arquitetura, OpenAPI
           gerado a partir do código [requirements, design]
  A10 ci_pipelines sem stages de lint, test ou security (ou sem CI)
        -> geração e configuração assistida de pipeline [deployment]
  A11 deploy_automation sem deploy no pipeline + manual_hints
        -> geração de pipeline de deploy e IaC [deployment]
  A12 logging_practice com print dominante / sem monitoring_tooling
        -> estruturação de logs e instrumentação assistida [monitoring]
  A13 weak_error_handling alto
        -> revisão assistida do tratamento de erros [development,
           monitoring]
  A14 duplication_pct alto ou similar_file_groups
        -> consolidação de duplicados e geração de boilerplate [development]
  A15 runtimes com eol = true ou sem dependency_automation
        -> upgrades e migrações assistidos [deployment]
  A16 ai_usage.in_development vazio
        -> ponto de partida: IA ainda não adotada no desenvolvimento;
           contrastar com a maturidade declarada

GUARDRAILS (sinal -> condição sobre as recomendações)

  G1  has_tests = false e ci_runs_tests = false
        -> primeiro criar a rede de segurança (testes gerados + CI) e só
           depois IA para refactoring
  G2  secrets_present = true
        -> remover e rodar segredos antes de usar ferramentas de IA no repo
  G3  sensitive_data_markers não vazio

  G5  history_confidence = low
        -> não afirmar tendências nem métricas de histórico sem confirmação

  G6  ai_usage.in_product preenchido e in_development vazio
        -> não tratar os SDKs como adoção de IA no desenvolvimento

==============================================================================
APÊNDICE B - REMOVIDO OU ADIADO, E PORQUÊ
==============================================================================

  Dados de plataforma (tempo de review, issues, falhas de CI, branch
  protection)
      Exigem API e token, não vêm do git. Módulo opcional futuro; até lá
      ficam em not_observable e vêm da conversa.
  Rework, fix-after-change, hotfix branches, ficheiros efémeros
      Sobrepõem-se a fix_commit_ratio e repeat_fix_files e são ruidosos.
  Complexidade e rácio de testes "ao longo do tempo"
      Exigem reconstruir versões antigas. Substituídos por
      test_commit_share_per_quarter, que sai do log.
  Grafo de imports e ciclos
      Custo alto e pouco fiável em linguagens dinâmicas. O change_coupling
      dá um sinal parecido só com git.
  Código morto
      Pouco fiável em Python e JavaScript.
  Idade das dependências e vulnerabilidades
      Precisam de base de dados externa (rede), o que quebra o determinismo.
  Ritmo de trabalho (commits à noite ou ao fim de semana)
      Indício fraco e eticamente delicado.
  Licenças, idioma dos commits, rácio de comentários
      Não alteram onde a IA ajuda.
  Indícios de testes manuais (checklists, Postman)
      Fracos. O Postman fica no inventário de ferramentas.
  Score composto de "prontidão para IA"
      Não é defensável perante um cliente. Substituído por guardrails
      explícitos.
  Métricas por pessoa
      Pouco fiáveis e eticamente problemáticas. Só agregados de equipa.
